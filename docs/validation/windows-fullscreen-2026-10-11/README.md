# Windows: автоматическая защита полного экрана

Проверенный исходный коммит `bd1ffc09283ea0ba2b645ba8c78afb2a80759b63`, версия `0.3.4`, ветка `windows/input-validation`. Команды выполнены непосредственно на физическом Windows 11 Pro 25H2, в интерактивной сессии пользователя. Git перед работой был чистым; выполнен fetch. Mac-код и публичный релиз не менялись.

## Поведение и стоимость

По умолчанию переходы блокируются, когда клиентская область активного окна покрывает выбранный монитор ПК, с допуском 1 пиксель для округления. Это охватывает borderless fullscreen и меню игры, а также полноэкранный браузер/видео. Список процессов, названия игр, заголовки окон и личные настройки не собираются. Размер обычного развёрнутого окна с заголовком/панелью задач не соответствует этому правилу. Игра на другом мониторе не блокирует выбранный экран.

`ForegroundGuard` получает только `EVENT_SYSTEM_FOREGROUND` глобально; `EVENT_OBJECT_LOCATIONCHANGE` ограничен процессом и потоком текущего активного окна и фильтруется по HWND/OBJID_WINDOW/CHILDID_SELF. События доставляются асинхронно на отдельный поток ввода. Повторные уведомления объединяются; проверяется текущее активное окно. Геометрия читается при смене фокуса/размера и непосредственно перед попыткой перехода, чтобы проверить состояние при задержавшемся уведомлении. Нет перечисления процессов/окон или постоянного таймера поиска игры. Регистрации снимаются при отключении защиты, разрыве соединения через штатный Disconnect и очистке потока.

Во время блокировки ordinary WM_TIMER проверки края отключён полностью; WH_MOUSE_LL и Raw Input на ПК остаются выключенными. Системный клавиатурный hook для удерживаемых клавиш/Ctrl+Alt+Esc сохранён, также продолжается обработка сети и звука. После снятия блокировки позиция переинициализируется: новое движение внутрь минимум на 6 пикселей и пауза 200 мс предотвращают мгновенный переход от курсора, оставленного у края. Переключатель в «Параметры → Игры и полный экран» применяется сразу и сохраняется локально.

Документация Microsoft: [асинхронная доставка SetWinEventHook и выбор процесса/потока](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwineventhook), [клиентские размеры окна](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclientrect), [преобразование в экранные координаты](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-clienttoscreen).

## Проверки финального EXE

Release self-contained win-x64, .NET SDK 10.0.401, TreatWarningsAsErrors: без предупреждений. EXE пересобран после публикации исходников, его версия/размер/SHA-256 находятся в `build.json`; именно этот EXE установлен на рабочем столе. Предыдущий EXE сохранён локально вне Git после полного штатного выхода старого EdgeLink.

- `input-checks.json`: 12/12; ответ потока за 0,0928 мс при блокировке UI на 300 мс. Дополнительно проверены регистрация/снятие/повторный запуск foreground hooks и геометрическая политика с отрицательными координатами, другим монитором, заголовком/панелью задач и допуском.
- `fullscreen-checks.json`: 8/8 на настоящем полноэкранном WinUI-окне. Проверены отключение таймера без mouse hook/Raw Input, живая смена настройки, переход фокуса на второе обычное окно, возвращение к полноэкранному окну, выход из полного экрана без смены фокуса по событию геометрии, Disconnect.
- `layout-checks.json`: 108 случаев, 0 ошибок, 96 DPI; повторные переключения, четыре размера, переносы текста и доступность нижних карточек при прокрутке.
- `tray-checks.json`: 8/8, без ошибок. Условия shutdown/updater проверены без выключения ОС/установки обновления.
- `.NET checks --ui-loop-check`: 39 PASS; loopback продолжает передавать зашифрованный ввод/звук при блокировке UI на 500 мс. Это программная проверка.

Новый `--fullscreen-checks` открывает собственные окна и меняет их presenter/фокус. Он не загружает настройки/ключ, не открывает сеть и не воспроизводит звук. Локальный Link без Connect и заведомо недоступные координаты края исключают захват/клипирование физической мыши. Защита отдельно наблюдает реальный экран с тестовым окном. Синтетические события мыши/клавиатуры не создаются.

WM_TIMER с запросом 16 мс не гарантирует 62,5 вызова/с или строгую задержку перехода.

## Живое окно и ограничения

Установленный EXE автоматически подключился к Mac, на главной обновляются аудиопакеты; новый раздел и включённый переключатель визуально проверены в нативном окне. На снимке были 2 аудиопрерывания; их причина/слышимость не установлены, отдельной проверки наушников на этом этапе нет. Окно штатно скрыто крестиком в трей, процесс остался работающим. Текущие ключи/настройки не публиковались.

Пользователь отложил проверку своей игры и мыши: «проверю сам и напишу», «потом». Реальная игра, FPS/frame time, плавность при 4000/8000 Гц и свежий физический A/B замер этой сборки остаются непроверенными. Предыдущий A/B отчёт для `0e09116` сохранён отдельно и не выдаётся за замер новой сборки. Реальные Alt+Tab и меню игры также ждут пользовательского результата: нативный fixture проверяет реальные события фокуса, но не воспроизводит конкретную игру или нажатие Alt+Tab.

Правило классифицирует активное окно по размеру и охватывает другие полноэкранные программы. Отдельная игровая эвристика/список процессов, оверлеи конкретных игр, эксклюзивный fullscreen, другие DPI и аппаратные изменения режима дисплея не проверялись. Следующий шаг — пользовательская проверка игры/переходов и при необходимости одинаковый пассивный observer плюс отдельный замер frame time. Перед публичным релизом объединить Mac-ветку `mac/el-icon-validation`; Mac-протокол этого изменения не требует.
